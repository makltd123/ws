# ws: контекстные рабочие пространства для Windows

## 1. Цель

Утилита `ws` для Windows 10/11. Рабочее пространство описывает один проект: какие приложения открыть, с какими папками, в каких позициях окон. Переключение между пространствами:

1. замораживает и прячет окна текущего пространства;
2. поднимает окна следующего (запускает, если ещё не запущено);
3. расставляет их по сохранённым позициям.

Это НЕ замена виртуальным рабочим столам Windows. Их внутренний API нестабилен, поэтому мы его не используем. «Пространство» это наша собственная сущность.

## 2. Стек и ограничения

- Python 3.11+, управление зависимостями через `uv` или `pip` + `pyproject.toml`.
- Библиотеки: `pywin32` (окна, COM), `psutil` (процессы, suspend/resume), `PyYAML` (манифесты), `typer` (CLI), `pystray` + `Pillow` (трей, этап 4).
- Никаких внутренних API виртуальных десктопов, никаких драйверов, никакого запуска от администратора.
- Ничего не убивать (`kill`/`terminate`) без явного флага `--close` и подтверждения.
- Все данные хранить в `%APPDATA%\ws\`. Репозиторий не должен писать вне этой папки.
- Код с типами, модули небольшие, на ключевые части тесты (`pytest`). Логирование через `logging` в `%APPDATA%\ws\ws.log`.

## 3. Структура проекта

```
ws/
  pyproject.toml
  README.md
  src/ws/
    cli.py            # typer-команды
    config.py         # пути, глобальный конфиг
    models.py         # dataclass'ы Space, Item, WindowRef
    manifest.py       # чтение/валидация YAML
    state.py          # state.json: что сейчас запущено и чьё
    winapi.py         # обёртки над win32: EnumWindows, SetWindowPos, ShowWindow, мониторы
    launcher.py       # запуск элементов и привязка новых окон к пространству
    freezer.py        # suspend/resume деревьев процессов
    switcher.py       # логика switch
    adapters/
      base.py         # интерфейс адаптера
      terminal.py     # Windows Terminal
      vscode.py
      browser.py      # Chrome/Edge с отдельным профилем
      explorer.py
      generic.py      # любое exe
  tests/
```

## 4. Модель данных

Манифест пространства: `%APPDATA%\ws\spaces\<name>.yml` (или `.workspace.yml` в корне репозитория проекта, см. этап 5).

```yaml
name: api-project
description: Бэкенд платёжки
env:                       # переменные окружения для всех запускаемых элементов
  GIT_AUTHOR_EMAIL: me@work.com
items:
  - type: vscode
    path: C:\proj\api
    window: {monitor: 0, x: 0, y: 0, w: 1280, h: 1040}

  - type: terminal
    tabs:
      - {dir: C:\proj\api, cmd: "uv run uvicorn app:app --reload", title: server}
      - {dir: C:\proj\api, title: shell}
    window: {monitor: 0, x: 1280, y: 0, w: 640, h: 520}

  - type: browser
    browser: chrome            # chrome | edge
    profile: api-project       # отдельный профиль = отдельная группа вкладок и процессов
    urls:
      - https://github.com/org/api
      - http://localhost:8000/docs
    window: {monitor: 0, x: 1280, y: 520, w: 640, h: 520}

  - type: explorer
    path: C:\proj\api\docs

  - type: app                  # generic
    exe: C:\Program Files\Obsidian\Obsidian.exe
    args: ["--vault", "C:\\proj\\notes"]

freeze:
  exclude: [Zoom.exe, Teams.exe, Spotify.exe]   # эти процессы не замораживать
```

Состояние `%APPDATA%\ws\state.json`:

- `active`: имя активного пространства или null;
- для каждого пространства: список привязанных окон `{hwnd, pid, exe, title, item_index}`, флаг `frozen`, время последней активности;
- при каждом чтении валидировать: если hwnd/pid уже не существуют, молча выкинуть запись.

Позиции задаются в координатах монитора (индекс монитора + смещение внутри него), чтобы раскладка переживала смену конфигурации экранов. Если монитора с таким индексом нет, падать на основной.

## 5. Ключевые проблемы и как их решать

1. **Привязка окон к пространству.** Многие приложения single-instance (VS Code, Chrome, Explorer), и pid запущенного процесса не равен pid окна. Решение: перед запуском снять множество видимых top-level окон, запустить, затем опрашивать (до 10 секунд, шаг 200 мс) и считать окна, которых не было в снимке и которые подходят под ожидание адаптера, принадлежащими этому элементу.
2. **Окна браузера.** Для браузера запуск идёт с `--user-data-dir=%APPDATA%\ws\profiles\<profile>` (отдельный профиль, процессы тоже отдельные). Это позволяет безопасно замораживать только его процессы: искать их по аргументу `--user-data-dir` в командной строке через `psutil`.
3. **Windows Terminal.** Раскладка вкладок задаётся только манифестом, из запущенного терминала её не вытащить. Запуск через `wt.exe -w new new-tab -d <dir> --title <t> <cmd> ; new-tab ...`. Аккуратно экранировать `;` и пути с пробелами.
4. **Окна администратора.** Если окно запущено от админа, а `ws` нет, управление им не сработает. Не падать: пометить элемент как `uncontrollable`, залогировать, показать предупреждение в выводе.
5. **UWP/Store-приложения.** Окна живут в ApplicationFrameHost. Для MVP не поддерживаются, обработать как generic с предупреждением.
6. **Заморозка.** Процессы с видео и звонками плохо переживают suspend, поэтому есть список `freeze.exclude` (и глобальный в `config.yml`). Исключённые процессы не замораживаются, но их окна всё равно прячутся (минимизируются).
7. **DPI и мониторы.** Включить per-monitor DPI awareness в начале процесса (`SetProcessDpiAwarenessContext`), иначе координаты поедут.

## 6. CLI (контракт)

```
ws list                          # пространства и статус (active / frozen / not running)
ws open <name>                   # запустить пространство (или показать, если уже запущено)
ws switch <name>                 # заморозить текущее, открыть указанное
ws freeze [<name>]               # заморозить активное или указанное
ws thaw <name>                   # разморозить без переключения
ws close <name> [--force]        # закрыть окна пространства (WM_CLOSE), с подтверждением
ws save <name>                   # снять раскладку текущих окон в новый манифест (этап 2)
ws edit <name>                   # открыть манифест в $EDITOR / блокноте
ws status                        # что сейчас активно и сколько процессов заморожено
ws doctor                        # проверить окружение: wt, code, chrome в PATH, DPI, права
```

Коды возврата: 0 успех, 1 ошибка пользователя (нет такого пространства), 2 системная ошибка.

## 7. Этапы и критерии приёмки

### Этап 1. Декларативный запуск и раскладка
Манифест → запуск элементов → привязка окон → расстановка.
Приёмка: `ws open api-project` на чистом рабочем столе открывает VS Code, Windows Terminal с двумя вкладками, Chrome с отдельным профилем и двумя URL, Explorer; окна встают по заданным координатам. Повторный `ws open` не плодит дубликаты, а выводит окна на передний план.

### Этап 2. Снимок раскладки
`ws save <name>` обходит видимые окна, определяет тип по exe (vscode, chrome/edge, explorer, windowsterminal, остальное generic), вытаскивает что можно (путь папки VS Code из командной строки; профиль и user-data-dir браузера; путь Explorer через `Shell.Application`), пишет манифест. Для терминала записать только позицию и пометить TODO-комментарием про вкладки.
Приёмка: после `ws save x` и закрытия всего `ws open x` восстанавливает ту же раскладку.

### Этап 3. Switch и заморозка
`ws switch b` при активном `a`: минимизирует и прячет окна `a`, замораживает их процессы (кроме исключений), открывает или размораживает `b`.
Приёмка: после переключения процессы `a` в состоянии suspended (проверить через `psutil`), CPU около нуля, возврат `ws switch a` восстанавливает работу без перезапуска приложений. Если один из процессов не заморозился, переключение продолжается и выводится предупреждение.

### Этап 4. Трей и горячие клавиши
Фоновый процесс `ws tray`: иконка, меню со списком пространств (активное отмечено), глобальные горячие клавиши (`Ctrl+Alt+1..9` для первых девяти пространств, задаётся в `config.yml`) через `RegisterHotKey`.
Приёмка: переключение из трея и по хоткею делает то же, что `ws switch`.

### Этап 5. «Где я остановился» и автоматизация
- При уходе из пространства сохранять заметку: последняя команда в терминале (если доступна через shell-хук, см. ниже), заголовок активного окна, время. Показывать при возврате в toast-уведомлении.
- Shell-хук для PowerShell: функция в `$PROFILE`, которая пишет cwd и последнюю команду в `%APPDATA%\ws\notes\<name>.json`.
- Автопереключение: опциональное правило в манифесте `triggers: {git_branch: "feature/payments"}`, `ws` при смене ветки в `path` предлагает (toast с кнопкой) переключиться.
- Манифест в репозитории: `.workspace.yml` в корне, команда `ws open .` берёт его.

## 8. Нефункциональные требования

- Переключение пространства с уже запущенными окнами занимает меньше 2 секунд.
- Падение любого адаптера не должно ломать остальные: ошибка логируется, элемент пропускается.
- Идемпотентность: повторный запуск любой команды не приводит к дубликатам окон и процессов.
- `ws` не должен менять системные настройки, реестр и автозагрузку без явной команды пользователя.

## 9. Порядок работы для Claude Code

1. Сначала прочитай этот файл целиком и предложи план файлов и интерфейсов (`winapi.py`, `models.py`) без написания логики. Дождись подтверждения.
2. Делай строго по этапам. После каждого этапа: запусти тесты, проверь приёмку руками там, где можно, и кратко опиши, что работает, а что нет.
3. Всё, что требует реального Windows GUI (запуск окон, расстановка), покрывай ручным чек-листом в `README.md`, а чистую логику (парсинг манифеста, раскладка координат по мониторам, привязка окон по diff-снимкам) тестами на моках.
4. Не добавляй зависимости сверх перечисленных без вопроса.
5. Если упрёшься в ограничение Windows, из-за которого пункт ТЗ не реализуем (например, нельзя получить cwd вкладки терминала), не изобретай обходные хаки: зафиксируй это в `README.md` в разделе «Известные ограничения» и предложи альтернативу.
